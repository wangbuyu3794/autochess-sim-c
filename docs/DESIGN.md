# 自走棋模拟设计总纲

## 1. 项目定位

项目展示名：自走棋模拟  
工程名：AutoChess-C  
主要目标：通过一个具有真实复杂度的自走棋模拟器，系统练习 C 语言工程能力。

本项目优先服务于学习，但不会刻意做成过于简单的练习题。代码应当接近成熟小型工程：模块边界清晰、数据结构稳定、行为可测试、后续可扩展。

## 2. 最终形态

终端版 `V1.0` 的目标是实现一个单机玩家 VS 电脑 AI 的自动战棋模拟器。程序可以自动购买英雄、部署阵容、触发羁绊、进入自动战斗，并通过多回合流程决出胜负。

终端版稳定后，`V2.0` 再考虑使用 raylib 制作图形界面。

## 3. 技术路线

初期推荐技术栈：

- C99 或 C11；
- CMake；
- 终端交互；
- 固定数组优先；
- CSV 或简单文本数据；
- 自写轻量测试；
- 中文用户输出；
- 英文代码命名。

## 4. 设计原则

### 4.1 固定数组优先

前期不优先使用复杂动态内存结构，而是通过固定数组管理单位、备战席、商店和棋盘。

这样更适合学习：

- 结构体数组；
- 索引管理；
- 边界检查；
- 数据生命周期；
- 调试和测试。

### 4.2 模板与实例分离

英雄固定配置和玩家拥有的具体单位必须分开。

示例：

```text
HeroTemplate：铁卫的基础配置
Unit：玩家拥有的某一个铁卫
BattleUnit：一次战斗中的临时铁卫状态
```

这样可以避免把“英雄种类”和“场上单位状态”混在一起。

### 4.3 战斗使用临时副本

战斗开始时，从玩家棋盘复制单位到战斗上下文。战斗中的扣血、死亡、移动只影响临时副本，不破坏玩家原始阵容。

### 4.4 随机数可复现

游戏应支持指定随机种子，例如：

```text
autochess --seed 12345
```

同一个 seed 应产生可复现的商店和战斗结果，方便测试与排错。

### 4.5 战斗属性分阶段加入

最终战斗系统会包含普通攻击、技能、攻击力、护甲、魔抗、法力值、最大法力值、暴击率、暴击伤害等概念。

但 `V0.1` 不一次性加入全部词条，只保留生命值、攻击力、阵营和存活状态。这样可以先把目标选择、扣血、死亡和胜负判断做稳定，再逐步扩展战斗公式。

### 4.6 索敌机制分阶段升级

`V0.1` 使用“攻击当前生命值最低的敌人”的临时索敌策略。该策略简单、稳定、容易测试。

`V0.2` 加入棋盘坐标后，索敌升级为：

1. 优先选择距离最近的敌人；
2. 距离相同时选择当前生命值更低者；
3. 仍然相同时选择实例编号更小者。

### 4.7 移动机制分阶段升级

`V0.2` 使用简单贪心移动：当目标不在攻击范围内时，单位优先尝试横向靠近目标，再尝试纵向靠近目标。目标格被占用、越界或两条方向都无法移动时，单位原地等待。

后续版本可以升级为 BFS 或 A* 寻路，以处理复杂阻挡和更自然的绕路。

## 5. 核心模块

| 模块 | 作用 |
|---|---|
| `common` | 通用类型、错误码、工具函数 |
| `config` | 全局常量，例如棋盘大小和最大单位数 |
| `hero` | 英雄模板数据 |
| `unit` | 玩家拥有的单位实例 |
| `player` | 玩家生命值、金币、等级、备战席 |
| `board` | 棋盘、部署、移动、位置检查 |
| `shop` | 商店刷新、购买逻辑、概率表 |
| `economy` | 收入、利息、升级经验 |
| `trait` | 羁绊统计和属性加成 |
| `battle` | 战斗上下文、目标选择、攻击、胜负判断 |
| `skill` | 技能系统 |
| `ai` | 电脑购买、刷新、布阵 |
| `command` | 终端命令解析，V1.1 支持准备阶段命令 |
| `save` | 保存和读取，后续扩展 |
| `logger` | 日志输出 |
| `game` | 主状态机和回合流程 |

这些模块不会一次性全部实现，而是按照路线逐步加入。

## 7. 协作方式

每个版本推进时遵循：

1. 先确认版本目标和不做什么；
2. 再设计数据结构和模块接口；
3. 实现最小可运行代码；
4. 编译并运行测试；
5. 用适中深度解释本次更新；
6. 更新文档和变更记录。

解释重点是：当前进度、加了什么、怎么加的、为什么这样做、后续还要做什么。

## 8. V0.3 数据分层

从 `V0.3` 开始，单位数据分为三层：

```text
HeroTemplate：英雄固定配置，例如名称、基础生命值、攻击力、攻击距离
Unit：玩家拥有的单位，例如实例编号、星级、所在位置
BattleUnit：一次战斗里的临时单位，例如当前生命值、战斗坐标、存活状态
```

这样的分层可以避免战斗过程直接破坏玩家阵容。后续加入升星、装备、羁绊和存档时，也更容易维护。

## 9. V0.4 商店与经济分层

从 `V0.4` 开始，准备阶段增加两个模块：

```text
economy：负责金币、收入、利息、经验和升级
shop：负责商店槽位、刷新、等级概率和购买
```

商店展示的是英雄模板。玩家购买后，英雄模板会变成玩家拥有的 `Unit`，并进入备战席。

当前商店概率只在已有英雄费用范围内工作。后续加入更多 3 费、4 费英雄后，再扩展完整概率表和共享卡池。

## 10. V0.5 升星策略

升星属于玩家拥有单位管理，因此实现放在 `player` 层。

规则：

```text
3 个同模板同星级单位 -> 1 个更高星级单位
```

当前实现保留找到的第一个单位作为合成结果，另外两个单位标记为 inactive。这样可以避免立即压缩数组带来的索引移动问题，更适合当前阶段学习和调试。

如果保留单位已经部署在棋盘上，升星后继续保持原位置。如果保留单位在备战席，升星后继续保留在备战席。

战斗开始时，`Unit` 会根据星级复制成 `BattleUnit`：

| 星级 | 生命值倍率 | 攻击力倍率 |
|---:|---:|---:|
| 1 | 1.0 | 1.0 |
| 2 | 1.8 | 1.7 |
| 3 | 3.2 | 3.0 |

## 11. V0.6 羁绊策略

从 `V0.6` 开始，英雄模板拥有两个羁绊字段：

```text
class_trait：职业，例如守卫、剑士、游侠、法师
origin_trait：阵营，例如城邦、森林、元素、暗影
```

当前版本先实现两个可见效果：

```text
2 守卫：守卫单位增加 25 最大生命值
4 守卫：守卫单位增加 60 最大生命值
2 剑士：剑士单位攻击力增加 15%
4 剑士：剑士单位攻击力增加 35%
```

阵营羁绊先参与统计和数据建模，具体效果后续再加入。

羁绊不在单个单位创建时立即应用，而是在双方单位都进入 `BattleContext` 后统一计算一次。这样可以避免重复应用，也能保证每一方只根据自己的阵容获得加成。

## 12. V0.7 法力与技能策略

从 `V0.7` 开始，英雄模板增加技能相关字段：

```text
initial_mana：初始法力值
max_mana：最大法力值
skill_id：技能编号
```

战斗单位复制模板后，会拥有当前法力值、最大法力值和技能编号。普通攻击后获得固定法力值；当当前法力值达到最大法力值时，单位会释放技能并清空法力值。

当前技能系统先实现单体技能和自我治疗：

```text
铁壁护盾：治疗自己
破势斩：对当前目标造成额外攻击伤害
连珠箭：对当前目标造成固定伤害
火球术：对当前目标造成较高固定伤害
```

技能释放逻辑放在 `skill` 模块，战斗循环只负责判断满蓝并触发技能。这样后续可以继续扩展群体伤害、控制、护盾、治疗、回蓝等效果。

## 13. V0.8 运营 AI 策略

从 `V0.8` 开始，电脑玩家拥有一个简单运营 AI。

当前 AI 不直接绕过规则修改玩家数据，而是调用已有接口：

```text
shop_refresh_for_player
shop_buy_slot
player_deploy_from_bench
```

这样 AI 会自然遵守金币、商店槽位、备战席、部署区域和等级上限。

当前评分规则：

```text
英雄评分 = 费用 * 100 + 攻击力 * 3 + 生命值 + 攻击距离 * 10
单位评分 = 英雄评分 + 星级 * 200
```

AI 会在商店中选择可购买的最高评分英雄，并把备战席中评分最高的单位部署到预设站位。后续可以继续扩展羁绊匹配奖励、阵容位置需求、刷新决策和升星优先级。

## 14. V0.9 完整对局循环

从 `V0.9` 开始，项目拥有 `game` 模块来调度完整对局。

`GameContext` 保存：

```text
玩家
敌方
双方商店
双方下一个实例编号
当前回合数
游戏结果
```

每回合流程：

```text
准备阶段
  -> 双方购买和部署
  -> 复制部署单位到 BattleContext
  -> 应用羁绊
  -> 自动战斗
  -> 根据存活单位结算扣血
  -> 判断游戏是否结束
```

当前扣血规则：

```text
扣血 = 基础扣血 + 胜方存活单位数量
```

这个规则简单、稳定，适合当前阶段测试。后续可以替换为更细的扣血公式，例如按星级、费用或回合数计算。

## 15. V1.0 终端发布版

`V1.0` 将第一阶段收束为一个可直接运行的终端模拟器。

启动参数：

```text
--help              显示帮助
--version           显示版本号
--quiet             只输出最终结果
--rounds <数量>     设置最大回合数
--player-seed <值>  设置玩家商店随机种子
--enemy-seed <值>   设置敌方商店随机种子
```

这一版的重点是稳定运行、可复现、可测试和中文友好输出。交互式命令系统、保存读取和外部数据文件不再强塞进 `V1.0`，而是作为后续版本继续演进，避免第一阶段没有明确终点。

## 16. V1.1 交互式准备阶段

`V1.1` 开始加入玩家可操作的准备阶段。默认模式仍然自动模拟；使用 `--interactive` 后，玩家可以在每回合战斗前输入命令。

当前命令：

```text
help       查看命令
status     查看玩家状态
shop       查看商店
bench      查看备战席和已上场单位
buy <1-5>  购买商店中的英雄
refresh    刷新商店
auto       自动部署当前最强单位
ready      结束准备并进入战斗
quit       退出本局
```

这一版没有直接实现复杂坐标布阵命令，而是通过 `auto` 和 `ready` 复用已有 AI 部署逻辑。这样可以先把“玩家操作 -> 规则接口 -> 战斗阶段”的链路打通，后续再逐步加入 `deploy`、`move`、`bench` 等更细的手动操作。

## 17. V1.2 手动部署

`V1.2` 在交互式准备阶段加入基础站位命令。

当前命令：

```text
deploy <备战席> <行> <列>           部署备战席单位
move <旧行> <旧列> <新行> <新列>    移动已上场单位
recall <行> <列>                    撤回指定坐标上的单位
```

这些命令不直接改写单位状态，而是调用 `player` 模块已有接口。因此它们会自然遵守玩家半场、占位、等级上限、备战席是否为空等规则。

`ready` 仍然会自动补位剩余可上场单位。这样新玩家可以只手动摆关键单位，其余交给系统补齐；后续如果需要更纯粹的手动模式，可以再加入“锁定阵容”类命令。

## 18. V1.3 经济命令

`V1.3` 让准备阶段开始具备基础运营取舍。

新增命令：

```text
sell <编号>  出售单位
buyxp        购买经验
```

出售规则：

```text
1星：返还 1 个原价
2星：返还 3 个原价
3星：返还 9 个原价
```

这个规则和三合一升星保持一致，便于理解和测试。出售逻辑放在 `player` 模块中，命令层只负责解析编号和输出结果。

`status` 和 `bench` 的状态展示会显示金币、等级、经验进度、上场人数和下回合收入，帮助玩家判断是刷新、买英雄、买经验还是存钱。

## 19. V1.4 商店锁定与回合体验

`V1.4` 加入商店锁定，并调整交互模式的回合开始体验。

新增命令：

```text
lock  锁定或解锁当前商店
```

规则：

```text
回合开始：结算收入
  -> 如果商店未锁定，免费刷新商店
  -> 如果商店已锁定，保留商店并自动解锁
```

手动 `refresh` 仍然花费 2 金币。这样“自然回合刷新”和“主动刷新”被区分开，更接近自走棋玩家的直觉，也能让锁店命令有明确价值。

`Shop` 自身保存 `is_locked` 状态，主循环只调用商店模块提供的回合准备接口，避免把商店规则散落在入口层。
