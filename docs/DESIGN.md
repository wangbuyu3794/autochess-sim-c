# 自走棋模拟设计总纲

## 1. 项目定位

项目展示名：自走棋模拟  
工程名：AutoChess-C  
主要目标：通过一个具有真实复杂度的自走棋模拟器，系统练习 C 语言工程能力。

本项目优先服务于学习，但不会刻意做成过于简单的练习题。代码应当接近成熟小型工程：模块边界清晰、数据结构稳定、行为可测试、后续可扩展。

## 2. 最终形态

终端版 `V1.0` 的目标是实现一个单机玩家 VS 电脑 AI 的自动战棋游戏。玩家可以购买英雄、调整阵容、触发羁绊、进入自动战斗，并通过多回合流程决出胜负。

终端版稳定后，`V2.0` 再考虑使用 raylib 制作图形界面。

## 3. 技术路线

初期推荐技术栈：

- C99 或 C11；
- CMake；
- 终端交互；
- 固定数组优先；
- CSV 或简单文本数据；
- 自写轻量测试；
- 中文用户输出；
- 英文代码命名。

## 4. 设计原则

### 4.1 固定数组优先

前期不优先使用复杂动态内存结构，而是通过固定数组管理单位、备战席、商店和棋盘。

这样更适合学习：

- 结构体数组；
- 索引管理；
- 边界检查；
- 数据生命周期；
- 调试和测试。

### 4.2 模板与实例分离

英雄固定配置和玩家拥有的具体单位必须分开。

示例：

```text
HeroTemplate：铁卫的基础配置
Unit：玩家拥有的某一个铁卫
BattleUnit：一次战斗中的临时铁卫状态
```

这样可以避免把“英雄种类”和“场上单位状态”混在一起。

### 4.3 战斗使用临时副本

战斗开始时，从玩家棋盘复制单位到战斗上下文。战斗中的扣血、死亡、移动只影响临时副本，不破坏玩家原始阵容。

### 4.4 随机数可复现

游戏应支持指定随机种子，例如：

```text
autochess --seed 12345
```

同一个 seed 应产生可复现的商店和战斗结果，方便测试与排错。

### 4.5 战斗属性分阶段加入

最终战斗系统会包含普通攻击、技能、攻击力、护甲、魔抗、法力值、最大法力值、暴击率、暴击伤害等概念。

但 `V0.1` 不一次性加入全部词条，只保留生命值、攻击力、阵营和存活状态。这样可以先把目标选择、扣血、死亡和胜负判断做稳定，再逐步扩展战斗公式。

### 4.6 索敌机制分阶段升级

`V0.1` 使用“攻击当前生命值最低的敌人”的临时索敌策略。该策略简单、稳定、容易测试。

后续加入棋盘坐标后，索敌会升级为：

1. 优先选择距离最近的敌人；
2. 距离相同时选择当前生命值更低者；
3. 仍然相同时选择实例编号更小者。

## 5. 核心模块

| 模块 | 作用 |
|---|---|
| `common` | 通用类型、错误码、工具函数 |
| `config` | 全局常量，例如棋盘大小和最大单位数 |
| `hero` | 英雄模板数据 |
| `unit` | 玩家拥有的单位实例 |
| `player` | 玩家生命值、金币、等级、备战席 |
| `board` | 棋盘、部署、移动、位置检查 |
| `shop` | 商店刷新、购买逻辑、概率表 |
| `economy` | 收入、利息、升级经验 |
| `trait` | 羁绊统计和属性加成 |
| `battle` | 战斗上下文、目标选择、攻击、胜负判断 |
| `skill` | 技能系统 |
| `ai` | 电脑购买、刷新、布阵 |
| `command` | 终端命令解析 |
| `save` | 保存和读取 |
| `logger` | 日志输出 |
| `game` | 主状态机和回合流程 |

这些模块不会一次性全部实现，而是按照路线逐步加入。

## 7. 协作方式

每个版本推进时遵循：

1. 先确认版本目标和不做什么；
2. 再设计数据结构和模块接口；
3. 实现最小可运行代码；
4. 编译并运行测试；
5. 用适中深度解释本次更新；
6. 更新文档和变更记录。

解释重点是：当前进度、加了什么、怎么加的、为什么这样做、后续还要做什么。
